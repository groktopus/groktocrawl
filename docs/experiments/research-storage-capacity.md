# Retained-storage capacity probe design

[Issue #82](https://github.com/magnus919/groktocrawl-x/issues/82) tracks this
predeclared exploration under accepted [ADR-0071](../adr/experimental/groktocrawl-x/0071-store-research-evidence-independently-of-sessions.md).
The [capacity findings](research-storage-capacity-findings.md) record the executed
probe, exact commit, design-file digest, raw results and limits. The design below
was declared before those measurements. A later design change must have a new identifier; preserve failed runs.

## Question and scope

Can the isolated adapter retain source-heavy roots close to its 100 MiB logical
quota, keep small complete publications usable during bounded ingestion, and
restore the resulting exact bytes within the harness's existing resource limits?
Measure the cost and expose failures. This first probe does not decide production
SLOs, select a storage backend or compare policies/runtimes.

A 100 MiB root is not a 100 MiB export. The current complete revision and entire
base64-encoded bundle each have a 1 MiB canonical bound. Large staged sources can
remain in a root without appearing in its selected publication's reference closure.
Report staged source bytes and selected artifact bytes separately; never describe
success with a small selected artifact as exporting the whole source-heavy root.
The proposed 5 MiB IR ceiling in ADR-0071 remains unimplemented.

## Fixed first design: retained-storage-capacity/1

Run only in the explicit isolated Compose project. Keep PostgreSQL 17.11, one CPU,
512 MiB memory and the adapter's one CPU/256 MiB memory limits from
`compose.research-storage.yml`; record actual image digests and effective settings.
Keep the eight-slot connection guard, current transaction timeouts, 100 MiB/root,
1 GiB/scope, 10 MiB/source and 1 MiB canonical/bundle limits unchanged.

Use one fresh capacity database for this run, distinct from lifecycle-test and
restore databases. Explicitly install and migrate through schema 9. Run the
following phases once each in order; this is a feasibility sample, not a replicated
performance study. No retries of failed workload operations and no discarded warmup
runs. Verification/reopen operations are recorded separately from workload timing.

| Phase | Fixed workload | Required evidence |
|---|---|---|
| Sequential source-heavy root | One native complete-history root; eleven unique 9 MiB bodies, sequential reserve/commit | Exactly 99 MiB of source bodies plus descriptors; independent reopen of all sources; charge reconciliation |
| Concurrent ingestion and publication | Four fresh roots in one separate scope, each with eleven unique 9 MiB bodies; four writer tasks, each sequential internally | 396 MiB of large source bodies in aggregate, operation errors/counts/durations, per-root/scope charge checks |
| Publication during ingestion | A fifth task uses a separate small complete-history root in that concurrent scope; ten sequential reserve/commit/read publication cycles of one pinned fixture revision | Three audited outputs per publication, exact revision/source binding, start/end timestamps and number of cycles overlapping ingestion; no overlap means concurrency result inconclusive |
| Root quota boundary | On the sequential source-heavy root, attempt an additional 2 MiB reservation | Rejection before acquisition; unchanged charge, source count and current pointer |
| Scope reservation boundary | Separate scope; eleven roots with 100 MiB quotas; reserve a total of exactly 1 GiB using chunks no larger than 11 MiB and respecting each root quota | One additional byte rejected without side effects; cancellation releases all reservations and receipts follow existing semantics; this allocates logical reservations, not 1 GiB of body storage |
| Format boundary | Construct a valid bounded complete publication whose selected export exceeds the 1 MiB encoded bundle limit | Explicit export rejection with no truncation or mutation; exact source/revision/publication bytes remain readable |
| Backup and independent restore | Dump the capacity database after workload verification; restore into a separately created empty database | Verify every stored source's independently regenerated bytes/digest, root/scope charges, complete revision, publication and outputs, plus recorded operation receipts |

Generate bodies reproducibly from a versioned SHA-256 counter stream encoded as
ASCII hex, keyed by phase/root ordinal/source ordinal. Trim to exactly 9 MiB;
record the generation algorithm, seed and body digest. Do not repeat one short
block to obtain conveniently compressible storage. This is still synthetic text,
not a claim of representative enterprise corpus compression or semantics.

Reserve before generating each body. Each writer owns at most one body at a time;
never prebuild the whole corpus or spawn one task per source. Record the maximum
writer count, intended body-buffer bound (four times 9 MiB in concurrent ingestion)
and observed process memory separately: descriptors, driver copies, canonical
objects and runtime overhead can exceed the body-buffer figure. Use existing
small synthetic research/verifier fixtures, with human labels unset.

## Measurements and result contract

Emit a versioned `retained-storage-capacity-result/1` JSON report and raw per-operation
records. Keep errors and partial counts if a phase fails; do not emit a successful
report after a hard integrity failure. The run needs these fields:

- Identity: code commit, design ID/digest, source generator version/seed, UTC start
  and end, database schema/server version, Python/driver versions, image digests,
  host CPU/memory and effective container limits. Never include credentials or DSNs.
- Operations: phase/root ordinal, operation kind, monotonic start/end/duration,
  byte count, success or sanitized error type, attempted/succeeded/failed counts.
  Include reservation, source commit/read, publication reserve/commit/read,
  overflow, dump and restore operations with explicit timing boundaries.
- Summaries: per-kind sample count, minimum, median, nearest-rank p95 and maximum,
  plus aggregate bytes/elapsed time for each ingestion phase. Ten publication
  samples are only a small descriptive sample, not a stable tail-latency estimate.
- Storage: logical charges and exact body/canonical/output bytes; relation totals
  including indexes/TOAST; database size before/after; WAL LSN delta during the
  workload; dump format/size and dump/restore wall time. WAL delta is cluster-wide
  and must be labeled accordingly. Do not equate logical charge with disk use.
- Resources: sampled container CPU/memory, sampling interval and missing samples;
  adapter peak RSS with units/platform. Sampled maxima can miss short-lived peaks.
- Verification: complete expected/actual source and publication counts, manifest
  digests, mismatch count, quota and format boundary outcomes, overlap count, and
  explicit untested scenarios. Record dump/restore verification separately from
  the existing post-backup deletion reconciliation suite.

Use an outer twenty-minute cap for this probe, preserving existing per-operation
limits. The cap contains CI cost; it is not a storage SLO. A timeout, OOM, failed
write/read or verification mismatch is evidence to retain and investigate, not a
reason to increase limits silently. Existing required lifecycle/integration tests
remain mandatory and cannot be substituted with this probe.

## Interpretation and remaining gates

Integrity and quota assertions must all pass to describe the run as verified.
Report measured latency, footprint and backup cost as observations without an
invented performance pass mark. A single hosted run cannot establish variance,
noisy-neighbor resilience, sustained-load headroom, fairness, production reliability
or the acceptable footprint required for final W3 adoption.

This design leaves full 1 GiB physical scope occupancy, multiple processes, large
complete IR, long histories, vector contention, retention churn and production
backup/recovery targets unmeasured. It does not establish independent semantic
verification or represent the enterprise research evaluation workload. Use the
results to propose the next measured workload and thresholds before comparative
runs; do not promote the inherited baseline or accept W3 automatically.

Preserve databases/volumes for inspection. Do not add automatic volume deletion,
provider calls, public routes, Qdrant changes or a new recovery runtime. No accepted
ADR decision changes here; implementation detail is within the existing bounded
exploration scope.

## Probe implementation and execution

`tests/storage/run_capacity_probe.py` orchestrates the design with the existing
isolated Compose environment. Run it from the repository root after building the
storage-adapter image and starting the dedicated PostgreSQL service. It refuses
an existing `capacity-results` output directory or existing capacity databases.
`capacity_workload.py` emits append-only operation events and a compact external
manifest; `capacity_verify.py` reopens every source and regenerates its exact bytes
before and after restore. The large-export control uses a valid publication with
multibyte synthetic audit rationales; character bounds and canonical publication
admission pass while its base64 member alone exceeds the export byte limit.

The host records `capacity-results/result.json`, raw phase JSONL, the manifest,
resource samples and phase failure diagnostics. The logical dump stays in a host
temporary directory outside the uploaded artifact; its size/format/timings are
reported. This is an experimental fixture dump, not a production backup policy.
A failed or interrupted workload cannot produce a verified result. The host stops
any surviving named workload container after failure; it preserves database data.
The twenty-minute execution budget has bounded sampling/stop cleanup afterward.

Required Runtime CI runs the probe after the existing 268 database cases and
post-backup deletion rehearsal. Its database job allowance is now 35 minutes to
accommodate the additional twenty-minute probe and cleanup; the probe and existing
per-operation deadlines remain unchanged. Capacity artifacts upload even after
failure. Local pure tests cover reproducible unique corpus bytes, descriptive
statistics including failures, and a valid publication that exceeds the encoded
export limit. Actual database capacity and restore remain unverified until hosted
execution completes; no local Docker measurement is claimed.
